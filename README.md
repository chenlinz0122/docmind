# DocMind

上传自己的文档（PDF / TXT / MD），提问，拿到**带页码引用**的回答。

这是一个偏「个人文档问答」的实现：不做花哨的模型编排，把精力放在三件容易被忽略的事上——**PDF 按页解析、引用能回到第几页、检索不到就拒答**。

- 解析：`pypdf` 逐页抽文本，扫描件（没有文本层）直接报错提示先 OCR，而不是假装读到了内容
- 检索：手写 BM25（k1=1.5、b=0.75）+ jieba 分词；jieba 不在时退化成「英文词 + 中文二元组」，零依赖也能跑
- 回答：默认抽取式（按问题词重合挑原句），配了 OpenAI 兼容的 Key 才调模型；接口异常自动退回抽取式
- 引用：每个回答都带 `文档名 + 页码 + 片段编号 + 原文片段`，点开能对着原文核
- 拒答：检索分低于阈值直接拒答，不进生成环节

## 快速开始

```bash
git clone https://github.com/chenlinz0122/docmind.git
cd docmind
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

打开 http://127.0.0.1:8000 ，上传一份 PDF，然后在页面里提问。

```bash
# 也可以纯命令行用
curl -F "file=@你的资料.pdf" -F "title=课程讲义" http://127.0.0.1:8000/api/docs
curl -s http://127.0.0.1:8000/api/ask -H "Content-Type: application/json" \
     -d '{"question":"这本讲义里缓存淘汰策略是怎么讲的？"}'
```

Docker：

```bash
docker build -t docmind .
docker run -p 8000:8000 -v "$PWD/var:/app/var" docmind
```

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/docs` | 上传文档（multipart，`file` + 可选 `title`），解析切块入库 |
| GET | `/api/docs` | 列出已入库文档与库规模 |
| DELETE | `/api/docs/{doc_id}` | 删除文档及其索引 |
| POST | `/api/ask` | 提问，返回答案、引用、命中的片段与耗时 |
| GET | `/api/stats` | 文档数 / 片段数 / 平均块长 |
| GET | `/health` | 健康检查（Docker HEALTHCHECK 用） |

`/api/ask` 返回示例：

```json
{
  "answer": "Redis 支持 LRU 淘汰策略，常用作会话缓存。",
  "citations": [{"title": "缓存笔记", "page": 2, "chunk_id": "demo-1a2b3c#0", "snippet": "..."}],
  "abstained": false,
  "reason": "answered_offline",
  "hits": [{"chunk_id": "demo-1a2b3c#0", "page": 2, "score": 6.21}]
}
```

## 几个设计取舍

**为什么按页切块而不是整篇切。** 整篇切最简单，但引用只能给到「文档」，用户还得自己翻。按页切之后，每块都带着页码，回答里能直接写「第 3 页」，这是文档问答能不能被信任的分水岭。代价是跨页的句子会被切开，所以切块时把上一页尾巴的 60 字带到下一页开头。

**为什么先 BM25 不上向量。** 个人文档库通常几十到几百页，BM25 对「术语、编号、专有名词」的召回已经够用，且不需要 embedding 模型、不需要向量库，冷启动零成本。它的短板是同义改写（问「怎么退款」，文档写「售后处理流程」），这一条写在下面的 Roadmap 里，而不是假装不存在。

**为什么默认抽取式回答。** 没有 Key 也能跑、能演示、能被复现；抽取式还有个副作用是「不会编」——答案就是原文的句子。配了模型才走生成，且接口报错一律退回抽取式，不让外部服务成为可用性的单点。

**为什么加了检索阈值。** BM25 对任何问题都会给出非零分数，包括库里根本没有的问题。不设阈值，负样本问题会被拼出一个「像样但错误」的答案。这里把阈值放在检索层，低于它的片段根本不进生成。

## 已知限制

- 只有稀疏检索，同义改写的查询会漏；没有重排，长文档里靠前的块占优。
- 中文分词依赖 jieba 的默认词典，专业术语（新型框架名、缩写）常被切碎。
- 索引是全量重建 + JSON 落盘，几万片段以内够用，再大要换向量库或倒排索引服务。
- 表格、公式、双栏排版的 PDF 抽取质量取决于 pypdf，复杂版式会串行。
- 抽取式回答只是「把原文句子拼起来」，读起来不如模型生成的自然。

## Roadmap

- [ ] 加一路向量召回做混合检索，对比「纯 BM25」的 hit@k 与延迟
- [ ] 引用高亮：前端把命中的句子在原文里标出来
- [ ] 支持多文档对比问答（「这两份规范的差异在哪」）
- [ ] 把阈值与块大小做成可配置，写一组参数对比实验
